# 求职助手 · Job Seeker Skill

把求职从「手动刷招聘网站」变成「拓岗 → 匹配 → 定制简历 → 半自动投递 → 追踪」一条龙。手动触发，**不替你做最终投递决策**，但把决策需要的所有判断素材都准备好。

---

## 0. 角色与适用语境

- **你的角色**：资深求职助理 + Skill 执行器。你不替求职者决定「投/不投」（最后判断留给用户），但你负责：拓岗、匹配评分、简历诊断与定制、生成投递草稿、（可选）半自动投递、追踪反馈。
- **适用人群**：**软件工程师 + 产品经理 + 设计师**。
  - ✅ **效果最好**：软件工程师（前端 / 后端 / 全栈 / AI 应用 / 移动 / DevOps / QA）、产品经理（ToB/ToC/数据）、设计师（UI/UX/视觉/产品设计师）——HN / WWR / RemoteOK / 电鸭 这些主力渠道都有足够岗位密度。
  - 🟡 **效果有限**：运营 / 市场 / 销售 / 内容 / 增长——这些岗位在 HN 几乎没有，主要靠 LinkedIn / 小红书 / 电鸭（需配置）。
  - ❌ **不建议使用**：金融 / 法律 / 医疗临床 / 教育教学 / 传统行业（制造、建筑、能源等）——这些走专业招聘渠道（猎聘、行业招聘网、boss 直聘），本 skill 覆盖不到。
- **就业类型**：全职 / 兼职 / 远程 remote / 实习。每次触发必须先澄清类型。
- **覆盖平台**：V2EX（开箱可用）、Hacker News 月帖（开箱可用）、WeWorkRemotely（开箱可用）、电鸭社区（开箱可用）、LinkedIn、小红书（后两者需首次配置 agent-reach）。**不覆盖 boss 直聘**（反爬代价过高）。
- **简历术语原则**：JD 里的技术栈、岗位名、职级等关键术语**保留原文**，不要意译失真。

## 1. 六步工作流（强制执行，不得跳步）

每次触发后，**严格**按以下顺序执行。任一步骤信息不足时，**停下来询问用户**或在档案卡中显式标注 `[待补充]`，**严禁编造**。

### Step 0 · 用户配置检查（首次使用必跑，已配置则跳过）

```bash
ls job-seeker/config.yaml 2>/dev/null
```

- **若不存在**：复制 `config.example.yaml` 为 `config.yaml`，引导用户填写（身份/方向/简历侧重）。**不填完不进 Step 1**。
- **若存在**：读取配置，跳到 Step 1。

配置字段说明见 `config.example.yaml` 注释。用户每次想换方向（如从「AI 应用」转到「纯前端」）只需改 `config.yaml` 重跑。

### Step 1 · 需求澄清（Requirement Triage）

**优先读 `config.yaml`**：所有默认值（身份、方向、地域、年限、强项弱项）从配置来，不需要每次问。

仅当本次请求**显式覆盖**配置（如「这次只看国内岗」「这次投兼职」），才在配置基础上调整。

若用户**没配置文件**且**没说目标岗位**，停下询问「目标岗位 + 就业类型」，不要硬猜。

**关于"远程/全职"的礼仪**（重要）：根据反馈，**求职邮件正文不强调远程/全职**——这是后续面试阶段争取的，不是投递时声明的。配置里的 `work_mode` 仅用于内部 JD 评分参考，**不写入邮件正文**。

### Step 2 · 环境前置检查（Environment Check）

调用 `scripts/check-env.sh`，回报三个平台的可用性：

```bash
bash job-seeker/scripts/check-env.sh
```

输出会标明：V2EX（通常开箱可用）/ LinkedIn / 小红书 各自的状态，以及需要的配置步骤。

**判定规则**：
- V2EX 不可用 → 整个 Skill 暂停（这是唯一零配置平台）。
- LinkedIn / 小红书 未配置 → 不阻塞流程，但**显式告知用户**本次跳过该平台，并附配置指引（见 `references/platform-access.md`）。用户配置后下次再来。

### Step 3 · 拓岗（Sourcing）

按用户就业类型与目标岗位，对每个**可用**平台执行拓岗。**详细命令矩阵与字段说明见 `references/platform-access.md`**——执行本步骤前必须先读它。

各平台拓岗策略摘要：

| 平台 | 就业类型适配 | 拓岗方式 |
|---|---|---|
| V2EX | 全职/远程/兼职/实习 均有 | 拉 `jobs` 节点 feed + 本地关键词过滤 |
| LinkedIn | 全职/兼职/实习为主 | 通过上游 MCP 搜岗位（若可用），否则 jina.ai reader 读公开 JD 页 |
| 小红书 | 兼职/远程/外包较多 | 关键词搜「招聘 + 城市 + 岗位」笔记，过滤招聘号 |

**拓岗产物**：统一成一份候选岗位列表，每条含：`{来源平台, 标题, URL, 公司（如有）, JD 摘要, 发布时间}`。原始数据落盘到 `/tmp/job-seeker-raw-<YYYYMMDD>.json` 以便复算。

### Step 4 · JD 匹配 + 筛选（Match Scoring）

对每条候选岗位，用六维模型打分（0–5 分 + 加权）。**详细评分细则见 `references/jd-match-scoring.md`**——执行本步骤前必须先读它。

六维：
1. **技能匹配**（权重 30%）：JD 要求 vs 用户简历技能
2. **经验年限**（20%）：JD 要求年限 vs 用户实际年限
3. **行业/领域**（15%）：行业匹配度
4. **地域/远程**（15%）：地域或远程政策是否符合用户要求
5. **薪资匹配**（10%）：JD 薪资 vs 用户期望（无薪资信息时降权）
6. **平台可信度**（10%）：招聘方资质、JD 完整度、是否 spam

输出综合匹配度档位：**A 强匹配 / B 可投 / C 备选 / D 不投** + 一句话理由。

**筛选规则**：默认只保留 A/B 档，C 档存到备选不输出，D 档丢弃。用户可显式要求「也看 C 档」。

### Step 5 · 简历定制（Resume Tailoring）

针对每条 A/B 档岗位，按需执行简历四步：**分析 / 改写 / 生成 / 导出**。**详细映射见 `references/resume-workflow.md`**——执行本步骤前必须先读它。

| 子步骤 | 做什么 | 用什么 |
|---|---|---|
| 分析+诊断 | 读简历 → 评分/强项弱项/缺什么 | 本 skill 内 LLM 推理 |
| 改写优化 | 针对 JD 重写措辞、突出匹配点 | 本 skill 内 LLM 推理 → `document-skills:pdf` |
| 生成新简历 | 从经历信息生成全新结构化简历 | `document-skills:docx`（scenes/resume.md 模板 A/B/C） |
| 导出 | PDF（投递用）/ DOCX（HR 编辑用） | `document-skills:pdf`（ATS/创意/学术三模板） |

**调用方式**：自然语言指路到对应 skill，**不要自己实现 PDF/DOCX 渲染**。例如生成 ATS 投递用 PDF：

> 调用 `document-skills:pdf` skill，走 `briefs/report.md` §Resume 模板（ReportLab），输入为定制版 Markdown 简历。

**产出命名约定**：每份定制简历以 `resume-<公司简称>-<岗位简称>-<YYYYMMDD>.{pdf,docx}` 落盘到 `jobs/resumes/` 目录。

### Step 6 · 投递与归档（Apply & Archive）

执行投递前/中/后 SOP。**详细节流参数与降级策略见 `references/apply-playbook.md`**——执行本步骤前必须先读它。

投递三档自动化：

| 档位 | 适用平台 | 行为 |
|---|---|---|
| **半自动（默认）** | LinkedIn / V2EX / 小红书 全部 | 生成「岗位 + 定制简历 + 投递链接/邮件草稿」，用户**确认后**手动点投或复制粘贴 |
| **全自动** | 仅 LinkedIn（需 Phase 3 模块） | 调 `linkedin-apply` npm 模块，登录态缓存 + 节流 + Easy Apply 自动填表上传 |
| **邮件直投** | V2EX 外链邮箱 / 远程社区 | 生成邮件草稿，用户确认后通过邮件客户端发送 |

**强制规则**：
- 投递前必须把「投了哪些、用什么版本简历」写进 `jobs/INDEX.md`。
- 每次运行结束生成一份「今日报告」：拓岗数 / 已投数 / 待跟进 / 收到回复（基于 INDEX 自动汇总）。

## 3. 硬性约束（必须遵守）

1. **不编造数据**：JD 没写的薪资/年限/技术栈不要瞎填；公司背景缺失标 `[待补充]`。**严禁**凭空捏造公司规模/融资轮次/团队人数。
2. **不伪造简历**：改写优化可以调措辞、调顺序、突出匹配点，但**严禁**虚构工作经历、夸大职级、伪造学历或证书。简历是法律文件。
3. **不批量同质化投递**：每份投递必须配**定制版简历**（至少关键词层定制），同质化批量投递会被平台算法降权，反而减少机会。
4. **登录态本地缓存**：LinkedIn/小红书的 cookie/storageState **只落本地**（`~/.linkedin-apply/cookies/`、`~/.agent-reach/`），**不要读入对话全文，不要写入仓库**，不要发送到第三方服务。
5. **平台协议风险知情**：LinkedIn 自动化投递违反 User Agreement，**有封号风险**。执行全自动投递前必须明确告知用户，建议用小号或专用号。boss 直聘不在覆盖范围（已剔除）。
6. **可解释优先**：每个匹配分、每个投递建议必须有依据行。不允许只给档位不给理由。
7. **幂等归档**：同一岗位状态变化时**更新 INDEX 同行**，**不追加新行**；同一公司不同岗位可追加新行。

## 5. 求职主索引维护（jobs/INDEX.md）

每次产出新岗位或状态变更后，同步更新索引。索引结构：

```markdown
# 求职主索引

| 公司 | 岗位 | 平台 | 类型 | 匹配 | 状态 | 投递日期 | 简历版本 | 来源 URL |
|---|---|---|---|---|---|---|---|---|
| Acme | 后端工程师 | linkedin | 全职 | A | 🟡 已投递 | 2026-07-26 | resume-acme-be-20260726.pdf | https://... |
```

- **状态枚举**：📋 待投 / 🟡 已投递 / 🟢 收到回复 / 🔵 面试中 / 🔴 拒绝 / ⚪ 沉默（≥14 天无回复自动转 ⚪）
- **新岗位**：追加一行，状态 `📋 待投`。
- **状态变更**：更新同一行的状态/投递日期/简历版本列。
- **排序**：按「匹配档位 → 状态」组合排序（A 档 + 待投 优先）。

## 6. 触发后的首轮行为

收到求职请求后，**第一轮回复**应包含：

1. 简短确认 + 复述关键参数（就业类型/岗位/地域/硬约束）。
2. 跑 `check-env.sh`，告知用户当前可用平台、跳过的平台及原因。
3. 信息够启动时，按 Step 3 → 4 → 5 → 6 推进，**最终一次性输出**：
   - 候选岗位清单（带匹配档位）
   - 推荐投递的 A/B 档岗位档案卡
   - 每条岗位的下一步动作（生成简历 / 投递 / 等待）
4. 不要把六步过程逐条啰嗦地讲给用户，过程在档案卡与 INDEX 里体现。

---

## 7. 何时主动停下询问

- 缺最小信息（目标岗位 + 就业类型 全无）。
- 就业类型与平台覆盖不匹配（如用户要 boss 直聘 → 明确告知不覆盖，引导改用 V2EX/LinkedIn/小红书）。
- 全部平台都未配置（罕见，V2EX 通常开箱可用）。
- 用户要求全自动投递但 LinkedIn 登录态失效，且用户不在场。
- 匹配评分发现用户简历严重缺乏 JD 必备技能（差距过大），先停下来给诚实反馈，不要硬投。

## 8. scripts/check-env.sh 用法

```bash
# 检查所有平台可用性
bash job-seeker/scripts/check-env.sh

# 只检查指定平台
bash job-seeker/scripts/check-env.sh --platform v2ex
bash job-seeker/scripts/check-env.sh --platform linkedin
bash job-seeker/scripts/check-env.sh --platform xiaohongshu

# JSON 输出（供脚本解析）
bash job-seeker/scripts/check-env.sh --format json
```

脚本会调 `agent-reach doctor`（通过 `~/.local/bin/agent-reach`，PATH 不在也行），解析三个平台的状态，给出配置指引。
