# 设计规格：Invoice OCR 高度自动化录入

- 日期：2026-06-25
- 状态：修订待确认
- 范围：`invoice-ocr/`

## 1. 背景

当前流程已经支持图片识别、供应商模板、Excel 追加、批量处理和异常复核，但客户仍需要理解目标表、模板和确认步骤。新供应商默认进入人工确认，也导致正常票据无法从“拍照”直接走到“录入完成”。

本次设计把默认交互改为：首次完成一次目标表初始化，之后用户只需发送单张或多张票据照片；系统自动识别、自动学习版式、自动写表，仅在无法可靠完成时请求确认。

## 2. 目标

1. 没有目标表时，引导用户上传 Excel 模板或提供表头字段，并保存为最后使用的目标表。
2. 已有目标表时，自动复用最后一次使用的表，只告知用户，不等待确认。
3. 单张和批量图片使用同一条处理流水线。
4. 新供应商在数据完整且校验通过时，自动建立供应商模板并写入 Excel。
5. 已有供应商模板时，自动应用模板并写入 Excel。
6. 正常票据不产生确认步骤；异常票据在批次结束后统一请求用户处理。
7. 用户纠正仍写回供应商模板，后续同类票据自动应用。
8. 保留现有“供应商原文 + 面料款号原文”价格变化比对和 Excel 单价标红逻辑。
9. 目标表表头不依赖不断扩大的固定别名字典；未知表头由 LLM 在受约束字段集合中推断，并将确认后的映射持久化复用。

## 3. 非目标

- 不新增独立 OCR 服务、数据库或管理后台。
- 不扩展现有价格变化识别规则，也不增加聊天消息价格预警。
- 不重构现有 Excel 列定义和业务字段含义。
- 不在本次把服装送货单的内部字段模型改造成任意行业、任意票据的动态 Schema。
- 不允许 LLM 创建新的内部字段、执行 Excel 内容或直接决定文件写入位置。
- 不要求所有低质量图片强制写入 Excel。
- 不在本次实现中解决多用户同时写同一 Excel 的并发协作问题。

## 4. 方案选择

### 方案 A：所有新供应商都确认后录入

数据风险较低，但首次遇到每家供应商都会打断用户，不满足高度自动化目标。

### 方案 B：所有识别结果无条件写入

操作最少，但模糊图片、关键字段缺失和金额不一致也会直接污染目标表。

### 方案 C：正常自动处理，异常集中确认

新供应商不再天然等于异常。系统根据结构完整性和业务校验决定是否自动录入，并在批次结束后统一展示异常。

采用方案 C。

## 5. 用户体验

### 5.1 首次使用且没有目标表

用户发送图片后，系统暂停该批次并只询问一件事：

> 还没有设置录入表。请上传一个 Excel 模板，或者直接告诉我要使用的表头字段。

两种初始化方式：

1. 用户上传 Excel：读取当前活动工作表的第一行作为表头，校验文件可读、工作表存在且至少有一个可映射字段，保存为最后使用的目标表，然后自动继续处理原批次。
2. 用户提供表头字段：创建一个新 Excel，第一行按用户给出的顺序写入表头，完成字段映射后保存为最后使用的目标表，然后自动继续处理原批次。

表初始化成功后不再要求用户重复选择。

表头按“已学习映射 → 标准字段精确匹配 → LLM 推断”的顺序适配。高置信度映射自动使用并保存；低置信度或冲突映射一次性集中请用户确认。无法映射的自定义列原样保留并留空；如果所有字段都无法映射，系统不创建不可用的默认表。

### 5.2 已有目标表

收到图片后立即开始处理，并发送非阻塞提示：

> 本次继续录入到《目标表.xlsx》，我先处理。

用户无需回复“确认”。

### 5.3 更换目标表

用户上传新 Excel 并表达“以后录到这张表”或“换表”时：

1. 校验新表。
2. 更新最后使用的目标表。
3. 后续批次自动使用新表。

### 5.4 单张和批量图片

- 单张图片视为大小为 1 的批次。
- 多张图片一次接收、并行识别、统一写表。
- 处理中只提供必要进度，不逐张要求确认。
- 正常票据先完成录入，异常票据在批次末尾统一汇总。

## 6. 自动处理状态机

每个批次依次经过以下状态：

1. `WAITING_FOR_TABLE`：没有目标表，等待 Excel 模板或表头字段。
2. `READY`：目标表可用，准备处理图片。
3. `EXTRACTING`：并行识别图片并提取结构化数据。
4. `VALIDATING`：执行字段完整性、金额和模板匹配检查。
5. `LEARNING`：为符合自动录入条件的新供应商保存模板。
6. `EXPORTING`：把正常票据追加到目标表。
7. `NEEDS_REVIEW`：批次存在异常，统一向用户展示。
8. `COMPLETED`：批次正常完成。

批次级失败不应由单张票据失败触发。只要目标表可写，成功票据应继续完成录入。

## 7. 通用目标表适配层

### 7.1 内部字段模型

本次仍使用现有稳定内部字段，例如：

- 单据级：`note_number`、`date`、`customer`、`supplier_name`
- 明细级：`style_number`、`material_type`、`material_name`、`fabric_code`、`color_code`、`unit_price`、`quantity`、`unit`、`total_amount`、`remark`

目标表表头可以自由命名，但最终必须映射到上述允许字段之一或明确标记为“不写入”。LLM 不得创造未定义字段。

“描述”“件数”等现有用户维护列可以保留在目标表中，但在当前内部数据没有可靠来源时标记为“不写入”，不得由 LLM 猜值。

### 7.2 映射优先级

按以下顺序处理每个目标表：

1. **已学习映射**：按标准化后的有序表头签名读取历史确认结果，不调用 LLM。
2. **标准字段精确匹配**：只保留少量内部标准中文表头，例如“单号”“日期”“单价”“数量”，不维护不断扩大的业务别名字典。
3. **LLM 推断**：仅把尚未映射的表头、允许字段列表和字段中文说明交给 LLM。
4. **用户确认**：低置信度、重复目标字段或无法判断的结果一次性集中确认。
5. **持久化**：自动接受或用户确认后的结果保存到表头签名对应的映射记录，后续直接复用。

### 7.3 LLM 输出契约

LLM 必须输出结构化结果，每个未知表头包含：

- `header`：原始表头
- `target_field`：允许字段之一或 `null`
- `confidence`：`0.0` 到 `1.0`
- `reason`：简短判断依据，仅用于审计和确认提示

系统必须在程序侧验证：

- `target_field` 必须属于允许字段集合。
- 同一目标字段默认只能被一个表头占用。
- 原始表头必须来自当前工作表，不能由模型新增。
- 非法、缺失或不可解析的响应按“待确认”处理，不能静默写入。

### 7.4 自动接受与确认规则

- `confidence >= 0.90`、目标字段合法且没有冲突：自动接受并保存。
- `target_field = null` 且 `confidence >= 0.90`：自动标记为“不写入”，不打断用户。
- `confidence < 0.90`、多个表头指向同一字段或响应不完整：集中向用户确认一次。
- 用户明确纠正后，以用户映射为最高优先级并覆盖该表头签名的旧结果。
- 未确认的字段不写入；其他已确认字段仍可继续工作。
- 如果一个字段都无法可靠映射，目标表初始化暂停，不执行 OCR。
- LLM 不可用时，标准字段和已学习映射继续工作；剩余未知字段集中请用户确认，不降级为猜测。

### 7.5 表头签名与存储

表头签名由活动工作表中按顺序排列的表头计算。每个表头先执行 Unicode NFKC 规范化、去除首尾空白并合并连续空白；顺序和重复列名必须保留。映射记录保存：

- 表头签名
- 原始表头列表
- `header -> target_field` 映射
- 来源：`exact`、`llm` 或 `user`
- LLM 置信度
- 创建和更新时间

映射按表头结构复用，不绑定单一文件路径；相同表头结构的不同 Excel 可以共享已确认映射。

### 7.6 数据最小化与安全

- 默认只向 LLM 提供表头、目标表名称、允许字段及字段说明，不发送历史业务数据行。
- 表头和文件名按不可信输入处理，只作为 JSON 数据传入提示词。
- LLM 结果只参与字段映射，不执行公式、命令、路径操作或模板代码。
- Excel 中以 `=`、`+`、`-`、`@` 开头的普通文本值不得因映射过程被执行；写入策略沿用安全的单元格值处理。

### 7.7 本次通用化边界

该适配层使不同客户的 Excel 表头可以自动接入，但票据识别仍面向现有服装工厂送货单字段。要支持餐饮发票、物流单、医疗票据等完全不同字段，需要后续单独设计“可配置业务 Schema”，不在本次范围内。

## 8. 自动录入判定

### 8.1 已有模板

满足以下条件时自动录入：

- 供应商和单据标题匹配已有模板。
- 模板规则应用后不存在关键字段问题。
- 明细金额校验通过。
- 结果不是重复票据。

### 8.2 新供应商

新供应商不再默认进入人工确认。满足以下条件时自动创建模板并录入：

- 能识别供应商名称。
- 至少存在一行有效明细。
- 当前单据类型要求的关键字段完整。
- 每行存在可用的数量和单价。
- 行金额与“单价 × 数量”一致，允许绝对误差不超过 `0.01`。
- 明细金额合计与票据合计一致；票据没有合计时，使用明细合计。
- 没有 OCR 或模型明确标记的存疑字段。

自动模板应保存供应商、单据标题、字段布局、默认单位、手写字段特征和当前可复用的映射规则。

## 9. 异常定义

没有目标表时进入 `WAITING_FOR_TABLE` 并暂停批次，不执行 OCR，也不作为票据异常统计。

目标表已就绪后，以下情况进入批次末尾的异常确认，不自动建立新模板：

- 目标表在处理期间被删除、损坏或变为不可写。
- 目标表表头映射全部失败或存在尚未确认的关键冲突。
- 图片无法读取、严重模糊、不是支持的票据。
- 供应商无法识别。
- 没有明细行。
- 数量、单价等关键字段缺失或被标记为存疑。
- 行金额计算不一致或整单金额合计不一致。
- 已有模板匹配后仍存在字段冲突。
- 同一单号已存在于目标表。

重复票据默认跳过，不重复写入，并在结果摘要中告知用户。

异常展示必须包含图片或单号、供应商、具体问题和可执行回复示例。多个异常一次性展示，不逐张中断处理。

## 10. 批量处理语义

批量处理必须满足：

- 图片使用稳定文件标识去重，避免同一批次重复处理。
- OCR 可并行执行，Excel 写入必须串行。
- 输出顺序按文件名稳定排序，不能受并行完成顺序影响。
- 一个图片失败不回滚其他成功图片。
- 同一批次的新供应商正常票据可以自动建模板；后续同供应商票据复用该模板。
- 批次结束返回成功数、异常数、失败数、跳过重复数、写入行数和目标表名。

## 11. 数据与偏好

继续使用现有本地状态目录：

- `invoice-ocr-preferences.json` 保存最后使用的目标表，以及按表头签名索引的已学习映射。
- `invoice-ocr-templates/` 保存供应商模板和用户纠正规则。
- 每批次 `results.json` 保存处理结果和待复核状态。

偏好中的 `default_table` 语义调整为“最后一次成功使用的目标表”。只有目标表校验成功或成功写入后才能更新，不能把无效路径保存为默认值。

## 12. 输出与交互契约

正常完成：

> 已录入完成，共处理 8 张票据，写入 21 行，已保存到《采购入库表.xlsx》。

部分异常：

> 已先录入正常的 6 张票据，另有 2 张需要你确认。我把问题一次列在下面。

重复票据：

> 其中 1 张单号已录入过，本次已跳过，没有重复写入。

没有目标表：

> 还没有设置录入表。请上传一个 Excel 模板，或者直接告诉我要使用的表头字段。

用户纠正后：

> 这条我记下来了，下次这家同类单子会自动按这个规则处理。

表头映射需要确认：

> 这张表有 2 列我不太确定：“供货单位”是否是“面料厂家”，“结算价”是否是“单价”？你确认一次后，之后相同表头会自动使用。

对用户不得展示命令、内部路径、JSON、模板 ID、异常堆栈或内部状态名。

## 13. 模块边界

现有脚本职责保持清晰：

- `process.py`：批次状态机、目标表决策、自动录入判定、异常汇总。
- `table_schema.py`：内部字段目录、表头签名、映射校验和映射结果合并。
- `header_mapper.py`：调用现有 LLM 网关推断未知表头，不负责 Excel 写入。
- `templates.py`：模板匹配、模板自动创建、用户纠偏和目标表偏好。
- `extract.py`：图片识别和结构化提取，不负责用户交互决策。
- `export.py`：串行写入、重复检测、价格变化标红和写入统计。
- `SKILL.md`：面向 Agent 的自动化工作流和用户话术。

不把表初始化、模板学习、OCR 和 Excel 写入继续堆进单个函数；新增逻辑应通过小型纯函数表达判定规则，便于单元测试。

## 14. TDD 测试范围

实现阶段必须先写失败测试，再修改代码。至少覆盖：

1. 无目标表时返回表初始化请求，不启动 OCR。
2. 上传有效 Excel 后保存为最后使用表，并继续原批次。
3. 提供表头字段后创建 Excel 并保存偏好。
4. 已有目标表时自动复用且不等待确认。
5. 新供应商完整票据自动建模板并录入。
6. 新供应商关键字段缺失时不建模板并进入异常汇总。
7. 已有模板正常票据自动录入。
8. 批量处理中部分失败不影响其他票据写入。
9. 批量输出顺序稳定。
10. 重复单号跳过且不重复写入。
11. 用户纠正后模板规则被持久化。
12. 现有价格变化标红测试保持通过。
13. 已学习表头映射优先使用且不调用 LLM。
14. 标准表头精确匹配不调用 LLM。
15. 未知表头由 LLM 映射到允许字段。
16. 高置信度无冲突映射自动保存。
17. 低置信度、非法字段和重复目标字段进入一次性确认。
18. LLM 不可用或返回非法 JSON 时不静默写错列。
19. 相同表头签名的不同 Excel 复用同一映射。
20. 用户纠正表头映射后覆盖旧映射。

## 15. 验收标准

- 首次没有目标表时，用户只需上传 Excel 或给出表头字段一次。
- 设置目标表后，后续单张和批量图片无需选择表或确认正常票据。
- 新供应商的完整、无异常票据可自动建模板并写入。
- 所有异常在批次结束后统一展示。
- 批量任务中单张失败不影响其他成功票据。
- 重复票据不会重复写入。
- 用户纠偏会影响后续同供应商同版式票据。
- 未知目标表表头能够通过 LLM 自动映射到现有内部字段。
- 已确认的表头映射后续不重复调用 LLM。
- 低置信度和冲突映射只集中确认一次，未确认字段不写入。
- LLM 只能返回允许字段，不能创建字段或控制文件操作。
- 本次交付明确为通用目标表适配层，不宣称支持任意行业票据字段。
- 现有 Excel 价格变化标红行为不变。
- 自动化逻辑有单元测试，完整测试集通过。
- 实现不引入大面积 `try/except`、无意义防御性分支或与现有代码风格不一致的抽象。

## 16. 实施顺序约束

1. 用户确认修订后的 Spec。
2. 废弃原 Plan 中固定 `HEADER_ALIASES` 的实现方案，基于修订 Spec 重新生成 Plan。
3. 用户确认新 Plan。
4. 按 TDD 执行：测试失败、最小实现、测试通过、重构。
5. 完成后运行全量验证并提交验收结论。
